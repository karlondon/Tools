Hub WE ↔ NE DC Traffic Routing — Root Cause & Fix

Date: 2026-05-14  ·  Analysis: read-only Azure + PA NGFW config dump  ·  Tenant: 2a5c48c2-ebf9-4f92-89e5-18336e0787d2

Executive Summary

DC1/DC2 (WE) ↔ DC03/DC04 (NE) traffic bypasses the Palo Alto firewalls and flows directly via Global VNet Peering. This is caused by a route specificity conflict: the VNet peering system routes (/22) are more specific than the UDR entries in the AD subnet route tables (/16 or /8), so Azure's longest-prefix-match picks the peering route and bypasses the NGFW entirely.

🚨 The firewalls never see this traffic — confirmed by zero DC-to-DC hits in PA traffic logs on both PRD-LIN-NGFW-1 (WE) and PRD-LIN-NGFW-3 (NE).

2 Root Cause — Detailed

ℹ️ Azure uses longest-prefix-match. The most specific matching route wins, regardless of whether it is a UDR or a system/peering route.

WE AD Subnet → NE DC (e.g. 10.36.128.70 — NE DC03)

Route SourcePrefixNext-hopSpecificityResult
UDR OCG-WE-SHUB-ROUTE-To-ADDS-9 10.0.0.0/8 → WE NGFW 10.36.0.38 VirtualAppliance /8 ❌ LOSES
System (VNet Global Peering) 10.36.128.0/22 → peering VNetGlobalPeering /22 ✅ WINS
⚡ Traffic goes direct via peering — WE NGFW is bypassed entirely.

6 Why RPC 1722 Occurs Even When Traffic Flows via VNet Peering

❓ Question: repadmin /replsummary on DC1/DC2 shows DC03/DC04 with error 1722 "RPC server unavailable" — yet traffic appears to be flowing via VNet Global Peering and not hitting the NGFWs at all. Why?

Short Answer

The NSGs are not blocking the traffic. The 1722 errors are stale — they reflect the period when the NGFW had no routes and was actively dropping all inter-DC traffic. Peering-based connectivity between the hub DCs is permitted end-to-end. But the errors will not clear until a forced replication retry succeeds.

The Real Cause — Three Compounding Factors

Factor 1

NGFW was actively dropping all inter-DC traffic during the broken period

After the project revert, both NGFWs had zero IPSec tunnels and zero routes for the opposite region. The UDR on the WE AD subnet (10.0.0.0/8 → WE NGFW) is less specific than the peering system route (10.36.128.0/22), so hub DC-to-hub DC traffic bypasses the NGFW via peering. This is the correct path for basic IP connectivity.

However, during the window when the NGFW routes were misconfigured (or when other subnets use a more specific UDR that does force traffic through the NGFW), those connections were TCP RST / timed out. AD replication's RPC sessions were torn down. The DCs marked their replication partners as failed.

Factor 2

repadmin /replsummary shows the LAST attempt result, not current connectivity

repadmin /replsummary reports the last recorded replication outcome for each partner DC. If the last attempt failed (error 1722 — TCP connection refused/timeout from the NGFW drop period), that error persists in the output until a new successful replication cycle completes. The command is not a live connectivity test.

repadmin /replsummary output:
DC03 Last attempt @ 2026-05-13 14:32 FAILED, result 1722 (RPC server unavailable)
↑ This timestamp is from when NGFW was dropping traffic — not from right now
The peering path is now working, but no new successful attempt has cleared this entry yet
Factor 3

AD replication has exponential back-off — it won't retry immediately

After a replication failure, Windows AD uses an exponential back-off retry schedule. Following persistent failures the retry interval grows to up to 2 hours for cross-site replication. During this window, even though connectivity is restored, the DC will not attempt replication again until the timer expires. repadmin /replsummary continues to show the old 1722 error.
